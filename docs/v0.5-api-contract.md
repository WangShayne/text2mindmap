## 0. 现状（读代码得出的事实）

| 环节 | 现在怎么做 | 代码位置 |
|---|---|---|
| 音频解码与切段 | **全在浏览器**：解码成 16kHz 单声道；文件按 `ASR_SEGMENT_SECONDS`（默认 28s）在静音处切；录音每约 8s 切一段 | `web/src/audio/voice.ts`（`MicRecorder`）、`shared/wav.ts`（`planSegments`） |
| 段级时间 | 浏览器知道每段的 `{start,end}`（录音：`MicRecorder.onSegment` 的 `range`；文件：`planSegments` 的样本下标） | 同上 |
| ASR 请求 | 每段一次 `POST /api/transcribe`，服务端转发到 `{ASR}/audio/transcriptions`，`response_format=json`，**只取 `text`** | `server/asr.ts`、`server/app.ts:495` |
| 拼接 | 浏览器把各段文字用 `joinTranscript` 拼成**一段纯文本**，段边界和时间全部丢掉 | `web/src/audio/useTranscriber.ts` |
| 生成导图 | 用户点「生成」→ `POST /api/generate`（SSE），按 `LLM_CHUNK_CHARS`（12000 字）切块，每块一次 LLM，多块时再一次合并 | `server/generate.ts`、`server/chunk.ts` |
| 实时字幕 | `/api/realtime` WebSocket 代理 SenseVoice；事件 `partial/final` 带 `audioEnd`（服务端已收到的音频秒数，是**上界**，没有起点）；默认两遍模式，正文仍来自分段 ASR | `server/realtime.ts`、`shared/realtime.ts` |
| 存储 | `documents` 表只有 `markdown`；**音频和逐字稿都不落库** | `server/db.ts` |

### 0.1 SenseVoice 能给的时间粒度

- **能确定的**：段级时间，即「浏览器切出的 ASR 段」的起止，录音约 8s、文件 ≤28s，精确到样本。这是 v0.5 溯源的基础粒度。
- **实时链路**：只有 `audioEnd`（上界），没有句级起点；两遍模式下实时字幕最终会被分段结果替换，所以溯源**只用分段结果**，不用实时字幕。
- **句级 / 字级时间戳：未确认。** 现在请求的是 `response_format=json`。FunASR 的 sensevoice-server 部署文档（funasr.com/en/deploy/sensevoice-native-server.html，2026-10-23 查）列出的输出只有 JSON、SSE、`response_format=srt/vtt`（带时间轴的字幕）和 realtime WS，**没有提 `verbose_json` / `timestamp_granularities`**。SRT/VTT 说明服务端有分句（大概率按 VAD 切）的起止时间，但粒度没写，本机也没有可用的 ASR 服务，未实测。即使支持，Qwen3-ASR（`llama-server`）和云端 ASR 也不一定支持，所以 v0.5 **不依赖**句级时间戳。

结论：**v0.5 的溯源粒度 = ASR 段（slice，约 8–28 秒）**。

## 1. 术语

| 名词 | 含义 | 大小 |
|---|---|---|
| **slice（切片）** | 一次 ASR 请求对应的音频段及其文字。溯源最小单位 | 录音约 8s，文件 ≤ `segmentSeconds`（默认 28s） |
| **section（分节）** | 交给 LLM 提炼一次的一组连续 slice | 默认 10 分钟（可配 5–10 分钟），同时不超过 `LLM_CHUNK_CHARS` 字 |
| **refs（溯源映射）** | 导图节点 → slice 的对应关系 | — |

> 注意：PM 说的「长录音自动分段 5–10 分钟」= **section**，不是 ASR 切段。ASR 切段保持现状（≤28s），否则会超过云端 ASR 的 30s 限制。

## 2. 数据结构

```ts
// shared/transcript.ts（新增，前后端共用）

export interface Slice {
  /** 文档内唯一，按时间递增："s1"、"s2"… 由浏览器分配 */
  id: string
  /** 相对本次录音 / 本文件开头的秒数，保留 3 位小数 */
  start: number
  end: number
  /** 清洗后的文字（cleanTranscript 之后）；静音段为 "" */
  text: string
  /** 同一文档可以有多次录音 / 多个文件，用 take 区分时间轴 */
  take: number
  /** 'ok' | 'failed'（ASR 失败，text 为空，前端可提示重试） */
  status: 'ok' | 'failed'
}

export interface NodeRef {
  /** 节点在大纲树中的路径：根的子节点下标序列，根本身为 []。基于 parseMarkdown 的结果 */
  path: number[]
  /** 该节点来源的 slice id，按时间排序；可能跨多个 slice */
  sliceIds: string[]
  /** 由 sliceIds 推出：[最早 start, 最晚 end]，同一 take 内才有意义 */
  timeRange: [number, number]
  take: number
  /** 'slice' = LLM 标注且校验通过；'section' = 回退到整个 section 的范围 */
  precision: 'slice' | 'section'
}

export interface TranscriptDoc {
  version: 1
  slices: Slice[]
  refs: NodeRef[]
}
```

字段约定：
- `path` 而不是节点 id：Markdown 里没有稳定 id，`path` 由 `shared/outline.ts` 的 `parseMarkdown` 统一计算，前后端结果一致。用户手动编辑 Markdown 后 refs 可能错位，见 §6。
- 前端挂到 SimpleMindMap 节点 data 上时用 `data.t2m = { sliceIds, timeRange, precision }`，名字前端可自定。
- `timeRange` 是冗余字段，方便前端直接显示 `02:15–05:00`，以 `sliceIds` 为准。

### 2.1 节点 → slice 的映射怎么产生

1. **section 级（保证有）**：某 section 提炼出的所有节点，至少拿到该 section 的全部 slice（`precision: 'section'`）。
2. **slice 级（尽力）**：发给 LLM 的文本按 slice 加标记 `[s12] 文字…`，要求每个节点行尾带 `⟦s12,s13⟧`。服务端解析后**剥掉标记**再返回干净的 Markdown；标记缺失、引用了不存在或不属于本 section 的 id 时回退到 section 级。
3. **合并步骤**：合并 prompt 保留标记；合并后的节点取被合并节点 slice 的并集。合并时 LLM 丢标记 → 用节点文字和各 section 大纲做匹配兜底，仍匹配不上 → 该节点不带 refs（前端显示为「无来源」）。

> **未确认**：LLM 按要求保留 slice 标记的比例、对大纲质量的影响。需要用 30 分钟和 2 小时样本实测后，决定 slice 级是否默认开启。

## 3. HTTP 接口

### 3.1 `POST /api/transcribe`（不变）

请求 / 响应与 v0.4 一致：`{ ok: true, text }` 或 `{ ok: false, code, message }`。
slice 的 `id/start/end/take` 由浏览器维护，**服务端不需要改**。

### 3.2 `POST /api/generate`，新增 `mode: "transcript"`（文件 / 录音结束后的整篇生成）

请求：
```json
{
  "mode": "transcript",
  "title": "周会 10-23",
  "slices": [ { "id": "s1", "start": 0, "end": 27.6, "text": "…", "take": 1, "status": "ok" } ],
  "sectionSeconds": 600,
  "refs": true
}
```
- `sectionSeconds`：可选，钳制到 300–600，默认 600。
- `refs`：可选，默认 `true`，让 LLM 标 slice 级来源；`false` 时不发 `[sN]` 标记，只做 section 级。
- 校验（400）：`slices` 为数组且至少有一段非空文字；id 形如 `s123` 且唯一；`0 ≤ start ≤ end`；`take` 为正整数（默认 1）；`status` 为 `ok|failed`（默认 `ok`）；按 `(take, start)` 递增；最多 50000 段。所有 `text` 总长 > `MAX_INPUT_CHARS`（默认 200000）→ 413。
- 分节：连续 slice 按时间分节，一节从首段 `start` 到末段 `end` 不超过 `sectionSeconds`，且文字不超过 `LLM_CHUNK_CHARS`；**换 take 一定换节**；没有文字的节（全静音 / 全失败）直接跳过。
- `status:"failed"` 的 slice 不进 LLM、不出现在 refs 里，其余照常生成（单段 ASR 失败不影响整篇）。

响应：SSE（与现有 `mode: "full"` 相同的通道和事件名，新增字段向后兼容）：

| event | data | 说明 |
|---|---|---|
| `start` | `{ type, chunks, sections: [{ index, sliceIds:[first,last], timeRange }] }` | `chunks` = section 数，保持旧字段 |
| `progress` | `{ type, stage: "section", index, total, timeRange }` | 开始提炼第 index 节（index 从 1 开始；只有多节时发） |
| `section_done` | `{ type, index, total, markdown, refs }` | 该节大纲（refs 的 path 相对该节大纲）。前端可先把它画出来 |
| `progress` | `{ type, stage: "merge" }` | 开始合并 |
| `delta` | `{ type, text }` | 合并（或单节时）的流式文字，同现在 |
| `retry` | `{ type, reason }` | 同现在 |
| `done` | `{ type, markdown, refs }` | 最终大纲 + 全量 refs |
| `error` | `{ type, code, message, index? }` | `index` 有值表示第几节失败（从 1 开始）；无 `index` = 合并或单节失败 |

只有 1 个 section 时不发 `section_done` / `progress`，直接 `delta` + `done`（与现在单块一致）。
`delta` 里的 `⟦…⟧` 标记服务端已剥掉，前端拿到的就是干净 Markdown。
refs 规则：节点自己行尾的标记有效 → `precision:"slice"`；节大纲里没有有效标记 → 该节全部有文字的 slice（`"section"`）；合并后的节点丢了标记 → 按节点文字匹配各节大纲节点，取并集（`"section"`），仍匹配不上 → 无 refs。根节点（`path: []`）在合并结果里通常没有 refs。

### 3.3 `POST /api/generate`，新增 `mode: "incremental"`（实时录音中每 30–60 秒）

请求：
```json
{
  "mode": "incremental",
  "docId": "abc",
  "seq": 7,
  "title": "…",
  "markdown": "当前导图 Markdown",
  "refs": [ … ],
  "newSlices": [ … 上次增量之后新提交的 slice … ]
}
```
- 字段：`seq` 必填，非负整数（400）；`markdown` 可选，字符串，≤ 2,000,000 字（为空时以 `title` 为根新建）；`refs` 可选，只做形状校验后原样带回；`newSlices` 校验同 §3.2，可以全空；`tags` 可选，默认 `true`（`false` = 不发 slice 标记）。
- `seq`：前端每次 +1，服务端原样带回。服务端对同一「用户 + `docId`」（无 docId 时按用户）**同时只跑一个**增量；有在跑的再来请求，返回 `409 { error, code: "busy", seq }`，前端下个周期把新 slice 一起带上（合并请求，不排队）。
- 只用**已提交的分段结果**（两遍模式下 `/api/transcribe` 的结果；单遍模式下实时 final），不用 partial 字幕。
- 做法：LLM 只看「新 slice + 当前大纲的一、二级标题」，输出新节点要挂到哪个已有分支下（或新建分支）；**由服务端按标题文字合并进现有树**，不让 LLM 重写整棵树。这样成本固定、已有节点不变，前端视口不会被重置。

响应：SSE

| event | data |
|---|---|
| `start` | `{ type, seq, slices: n }` |
| `done` | `{ type, seq, markdown, refs, changes: { added: number[][], updated: number[][] } }` |
| `error` | `{ type, seq, code, message }` |

- `changes` 用 `path` 表示，路径基于返回的新 `markdown`。增量只追加，**不删除、不移动、不改名**：新节点都追加在兄弟节点末尾，所以已有节点的 path 不变，传入的 `refs` 原样有效。
  - `added`：新加子树的**根**路径（子树里的子节点不再单列）。前端用它做呼吸高亮。
  - `updated`：已有节点、其直接子节点变多了的路径。
  - 新节点的 refs 追加在返回的 `refs` 末尾：标记有效 → `"slice"`，否则 → 本次全部有文字的新 slice（`"section"`）。
- 合并规则：LLM 输出的一级项按文字（去标点空白、忽略大小写）匹配已有一级分支，匹配上就往里加，下一级同理；匹配不上就新建。
- 不调 LLM、直接 `done`（`changes` 为空、导图不变）的情况：`newSlices` 里没有有文字的 slice；LLM 回答 `NONE`。
- 录音期间导图**只读**（已定），所以不处理用户编辑冲突；前端按 `seq` 丢弃过期结果（`seq` 小于已应用的）。
- 过期判断放在前端，服务端不记 `seq`：服务端已用 409 保证同一文档同时只跑一个增量，不会并发产生乱序结果；如果服务端记最大 `seq`，前端刷新页面后 `seq` 从 0 重来，会被一直拒绝。
- 停止录音后：前端用全部 slices 调一次 `mode: "transcript"` 做最终整理（可选，由用户点「整理导图」触发，避免覆盖用户在录音结束后的修改）。

### 3.4 逐字稿保存（已定，已实现）

- 数据库：迁移 v3，`ALTER TABLE documents ADD COLUMN transcript TEXT;`（JSON，`TranscriptDoc`）。只加 nullable 列，旧文档为 NULL，旧客户端不受影响（不传 `transcript` = 不改）。
- `GET /api/docs/:id` → `{ doc: { id, title, markdown, transcript, created_at, updated_at } }`，`transcript` 为 `TranscriptDoc` 对象或 `null`。
- `POST /api/docs`、`PUT /api/docs/:id` 接受可选 `transcript`：
  - 对象 → 按 `TranscriptDoc` 校验后保存：`version` 必须为 1；`slices` 规则同 §3.2；`refs[].sliceIds` 必须都在 `slices` 里。不合法 → 400 `{ error }`，原数据不变。
  - `null` → 清空；不传 → 保持原值。
  - 序列化后 > 2,000,000 字 → 413。
  - 响应里的 `doc.transcript` 是保存后的值（数字已规整到 3 位小数，`failed` 段 `text` 置空）。
- `GET /api/docs`（列表）不返回 `transcript`。
- 用量：单篇 2 小时约 3–4 万字，JSON 约 0.1–0.2 MB。
- **不存音频**（已定）。

## 4. WebSocket `/api/realtime`（不变）

v0.5 **不改**实时字幕协议：事件仍是 `ready / partial / final / error / done / pong`，关闭码见 `shared/realtime.ts` 的 `CLOSE`。
增量导图走 §3.3 的 HTTP，不塞进这个 WS，原因：WS 是 ASR 代理，每个用户占上游一个名额，生命周期和 LLM 混在一起会互相拖累。

注意现有限制：`ASR_REALTIME_MAX_SECONDS` 默认 300 秒（随 SenseVoice `--max-audio-seconds`），超过后实时字幕以 1009 关闭，录音**降级为分段识别继续**。所以 1 小时录音里实时字幕只覆盖前 5 分钟，但增量导图依赖的是分段结果，不受影响。

## 5. 进度状态（文件 / 长录音）

前端状态机（ASR 在浏览器，LLM 在服务端）：

```
decoding → asr(done/total slices) → sections(index/total) → merging → done
                     ↘ error(slice i)        ↘ error(section i)  ↘ error
```

| 阶段 | 数据来源 |
|---|---|
| `decoding` | 浏览器本地（已有 `VoiceState.decoding`） |
| `asr` | 浏览器本地计数（已有 `VoiceState.file.done/total`） |
| `sections` / `merging` | §3.2 的 SSE `progress` / `section_done` |
| `done` | SSE `done` |

ASR 和 LLM 可以流水线化：前几个 section 的 slice 齐了就可以先发生成。**v0.5 先不做**，ASR 全部完成后再调一次 `mode: "transcript"`，简单可靠。

## 6. 错误与断连

| 场景 | 表现 | 前端处理 |
|---|---|---|
| ASR 某段失败 | `/api/transcribe` 返回 `{ ok:false, code }`（`AsrErrorCode`） | slice 标 `status:"failed"`，可单段重试；其余继续 |
| ASR 未配置 | 503 `not_configured` | 同现在 |
| LLM 错误 | SSE `error`，`code` ∈ `LlmErrorCode`（`auth / network / not_found / model / rate_limit / timeout / bad_response / upstream / not_configured / aborted`） | 整篇：已完成的 `section_done` 结果保留，可「从第 i 节重试」（**未确认是否 v0.5 做**） |
| 输入过长 | 413 | 提示调小或分次 |
| 增量并发 | 409 `busy` | 下个周期合并重发 |
| 增量过期 | 前端按 `seq` 丢弃 | — |
| SSE 中途断开 | 服务端 abort 上游 LLM（已有） | 显示「生成中断」，可重试 |
| 实时字幕断开 | WS 关闭码 1001/1008/1009/1011/4404/4409 → `DegradeReason` | 同 v0.4：降级为分段识别，增量导图继续 |
| 用户编辑后 refs 错位 | refs 按 path 失效 | 前端在 Markdown 被手动编辑后，按「节点文字 + 父路径」重新匹配；匹配不上的节点去掉 refs |

## 附录：现拼接方案基线（1 小时录音）

> 以下为**按代码和仓库内数据推算**，未在真实部署上实测。

### A. 文字量

- 仓库的 `scripts/asr-bench/audio/zh-5min`（FLEURS 普通话朗读）参考文本 1039 字 / 5 分钟 ≈ **208 字/分钟**。
- 1 小时 ≈ **1.2 万字**；会议口语语速更快，估 **1.2–1.8 万字**（上限未确认）。

### B. 调用次数

| 环节 | 次数（1 小时） | 依据 |
|---|---|---|
| ASR（文件上传） | 3600 / 28 ≈ **129 次**（静音处切，实际略多） | `ASR_SEGMENT_SECONDS=28`，`planSegments` |
| ASR（录音） | 3600 / 8 ≈ **450 次** | `MicRecorder` 段长 `min(8, segmentSeconds)` |
| LLM（现方案） | 1.2–1.8 万字 / 12000 → **2 块 + 1 次合并 = 3 次**；每次校验失败重试 1 次，最坏 **6 次** | `LLM_CHUNK_CHARS=12000`，`withRetry` 最多 2 次 |
| LLM（v0.5 方案 C，10 分钟一节） | **6 节 + 1 次合并 = 7 次**（最坏 14 次）；5 分钟一节则 13 次 | §3.2 |
| LLM（v0.5 实时增量，每 45 秒） | 约 **80 次**/小时 + 结束时可选 1 次整理 | §3.3 |

### C. 单价估算

- ASR：自托管 SenseVoice / Qwen3-ASR，**没有按量费用**，只有机器成本。云端 ASR 按服务商计价，未核算。
- LLM：默认模型 `gpt-4o-mini`（`LLM_MODEL` 默认值）。中文约 1 字 ≈ 1 token（按 o200k 分词粗估，**未实测**）。

| 方案 | 输入 token | 输出 token | 按 gpt-4o-mini 公开价 $0.15 / $0.60 每百万（价格**本次未复核**） |
|---|---|---|---|
| 现方案（3 次） | ≈ 1.5 万（正文）+ 0.3 万（大纲进合并）+ 提示词 ≈ **2 万** | ≈ **0.5 万** | ≈ **$0.006** |
| C 整篇（7 次） | ≈ 1.5 万 + 0.6 万 + 提示词 ≈ **2.3 万**（slice 标记另加约 10%） | ≈ **0.8 万** | ≈ **$0.008** |
| C 实时增量（80 次） | 每次 ≈ 新文字 0.02 万 + 标题上下文 0.05 万 + 提示词 0.05 万 ≈ 0.12 万 → **≈ 10 万** | 每次 ≈ 0.02 万 → **≈ 1.6 万** | ≈ **$0.025** |

结论：LLM 费用在任何方案下都是**几分钱 / 小时**量级；实时增量是整篇的 3–4 倍，仍然很低。换成更贵的模型按比例放大。
